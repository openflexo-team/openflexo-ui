# TokenMakers of the editors

The colouring of the FML editor is done by `FMLTokenMaker`, a class that **JFlex generates**. The generated Java is committed
(`src/main/java/org/openflexo/fml/controller/view/FMLTokenMaker.java`); nothing is generated by the build.

| File | Role |
|---|---|
| `src/main/resources/JFLEX/FMLTokenMaker.xml` | the definition of the language (keywords, operators, comments...), for TokenMakerMaker |
| `src/main/resources/JFLEX/FMLTokenMaker.flex` | the JFlex source that TokenMakerMaker produces from the definition |
| `src/main/resources/JFLEX/skeleton.default` | the JFlex skeleton of RSyntaxTextArea (the template of the generated class) |
| `src/main/java/.../FMLTokenMaker.java` | the generated class |

## Changing the Java generated from the `.flex` (no tool to install)

```
./gradlew :fml-technologyadapter-ui:generateTokenMakers
```

JFlex 1.4.1 is fetched by Gradle (the only version that the skeleton supports). The Java is a function of the `.flex`, the skeleton and
JFlex: running the task on the files as committed gives the committed class, but for the first comment lines, which hold the date.

## Changing the keywords, the operators... of the language

The `.flex` is **not edited by hand**: TokenMakerMaker builds it from the definition (`FMLTokenMaker.xml`), by filling the holes of a template
(`Template.flex`) with the keywords, the operators, the comments and the literals of the definition. The `.flex` of this directory is exactly what
TokenMakerMaker gives for the `.xml` (checked on 2026-10-22: no difference but the date of the first lines).

So, to change the language:

1. Edit `FMLTokenMaker.xml`. It is a plain list (`<keyword>`, `<operator>`...): a text editor is enough. Opening it in TokenMakerMaker
   (https://github.com/bobbylight/TokenMakerMaker, a Swing application; File, Open) is the other way.
2. Build the `.flex` from it, with TokenMakerMaker (Generate; it writes the `.flex` into the output directory that you set in File, Options) or
   without its window, see below. Put the `.flex` into `src/main/resources/JFLEX/`.
3. TokenMakerMaker also generates a Java class, with *its own* skeleton, which targets an old RSyntaxTextArea (3.1.3 for the last release):
   **ignore that Java**, and run `generateTokenMakers`, which uses the skeleton of this directory.

If a rule is needed that TokenMakerMaker cannot express, edit the `.flex` by hand, but then the `.xml` is no longer the source: the next
generation from the `.xml` would erase the change. Decide which of the two is the master and say it here.

### Building the `.flex` without the window

TokenMakerMaker has to be built once (`gradlew installDist` in its clone, giving `build/install/tmm`). This class only calls what the window calls:

```java
package org.fife.tmm;

import java.io.File;

public class FlexFromXml {
	public static void main(String[] args) throws Exception {
		TokenMakerInfo info = TokenMakerInfo.load(new File(args[0]));          // the .xml
		System.out.println(info.createFlexFile(new File(args[1])));             // the directory to write into (with the package folders)
	}
}
```

Compiled against `tokenMakerMaker-<version>.jar` and the jars of `build/install/tmm/lib`, then run with `-Djava.awt.headless=true`.

## When RSyntaxTextArea changes

The generated class extends `AbstractJFlexCTokenMaker`. When a new version of RSyntaxTextArea adds an abstract method to that base class, the
generated class stops compiling: add the method to **the skeleton** (that is what was done for `yystate()`, abstract in 3.6.3 and absent from
3.3.2), then run the task. Do not edit the generated Java.

## The editor of formod (B)

`BTokenMaker` (`formod/b-ta-ui`) has only its definition (`BTokenMaker.xml`) in the repository, not the `.flex`: its Java was generated outside
and `yystate()` was added by hand. To bring it to this procedure, generate its `.flex` with TokenMakerMaker, add it to the repository with a copy
of this skeleton, and give `b-ta-ui` the same task.
